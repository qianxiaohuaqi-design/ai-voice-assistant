## N1 — 旧同步请求体先验证导致错误码不一致

- **定位：** v1.1 §3.2；P0-04；本地 FastAPI 旧路由输入含必填 `SyncPayload`。
- **风险：** 如在函数体顶部拒写，则已认证 `{}` 等合法 JSON 可能提前由 Pydantic 返回 422，无法统一体现 `409 SYNC_UNSAFE`。
- **落实规则（不改业务设计）：** 停用写路由可改变签名/校验流程，仅保留必要认证、请求格式安全界限与“拒绝全部写入”的门禁；对**认证有效且 JSON 语法合法**的旧同步请求（含空对象/字段缺失）统一返回 HTTP 409 + `SYNC_UNSAFE`，在任何设置、Key、声音库或会话变化之前拒绝。JWT 不合法则 401。非 JSON 的传输错误仍按最小安全解析/HTTP 语义处理，绝不能落入旧写入代码。
- **验证：** 有效 JSON `{}`、缺失必填项、旧合法整包、包含额外字段均 409 且业务持久内容/Revision 不变；未认证 401；恶意/格式错误绝无写入；HTTP 错误不显示保存成功。
- **归属：** P0-04。**未实现/未测试**。

## N2 — D2 最近使用时间如何形成确定结果

- **定位：** v1.1 §4.2、§12；P1a，不属于 P0。
- **用户已确认不变：** 删除默认角色后，自动选择最近使用的剩余有效角色。
- **推荐的实现定义（仍待 P1a 具体落地检查）：**
  1. 在有账号身份且服务器验证所属角色的**主动选择/激活角色**操作成功后更新 `last_used_at`；成功创建新聊天 turn 并以该角色归属时也可更新（如采用此触发规则，则必须锁定并统一测试），角色编辑/SOUL 阅读不算使用。
  2. 纯 GET、登录后自动加载、轮询、后台 SOUL/Memory 整理、语音播放回调、定时任务不更新。
  3. `last_used_at` 非 null 优先，按时间 DESC；null 排最后；平局按 `created_at DESC`（null 排最后），再按稳定角色 ID **字典序 ASC**。同一事务确定继任默认并更新相关 `role_revision`，唯一约束保证至多一名活跃默认。
  4. 旧角色的缺失 `last_used_at` 不用“迁移时刻”伪造使用时间；是否纳入聊天创建这一额外事件需在 P1a 接口设计时一致落实，不能因 GET/轮询产生非预期变动。
- **验证：** null/时间相同/创建时间相同/并发删除默认/零活跃角色/恢复旧角色/GET 不改变结果。
- **归属：** P1a 授权前纳入现有权威 `doc/` 与测试。**D2 决议已确认，技术触发细节非已实施事实**。
